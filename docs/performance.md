### 해석

- 노드가 2,000개여도 명령 적용 p95가 0.4ms 안팎으로, 명세 목표인 p95 12ms보다 훨씬 작다. 명령마다 문서 전체를 다시 검증하지만 아직 병목이 아니다.
- JSON 읽기는 노드 2,000개에서 GC 때문에 p95가 다른 작업보다 크다. 읽기는 메인 스레드 밖에서 하므로 화면 프레임에는 영향이 없다.
- 실기기(2026-10-14, Galaxy Z Fold7 커버 화면 120Hz, release 빌드, `dumpsys gfxinfo`)에서 보드 스크롤 프레임은 p50 5 ms, p90 7 ms였다. 당시에는 보드 전용 샘플(sample-board)로 쟀고, 지금은 같은 화면이 sample-showcase의 대시보드 보드에 들어 있다.
  편집 중 위젯을 드래그할 때 놓친 프레임은 18.8%에서 6~9%로 줄었다. 드래그하는 동안 다른 위젯의 노드를 같은 객체로 유지하게 고친 결과다. API 26, 27 기기와 중급 기기에서는 아직 재지 않았다.

다시 재려면 `./gradlew :benchmarks:runBenchmarks`를 실행한다. 결과는 `benchmarks/build/reports/benchmarks/jvm.md`에 생긴다.

## 실기기 프레임

2026-10-18, Galaxy Z Fold7, 커밋 402a375의 release 빌드에서 쇼케이스를 조작하며 끊긴 프레임 비율을 쟀다.

| 화면 | 조작 | 끊긴 프레임 |
| --- | --- | ---: |
| 커버 화면 | 스크롤 | 0~0.3% |
| 커버 화면 | 동작 시트와 다이얼로그 열고 닫기 | 0.9% |
| 커버 화면 | 통화 화면 참가자 띠 스크롤과 고정 | 0% |
| 펼친 메인 화면 | 스크롤 | 0~0.45% |
| 펼친 메인 화면 | 팝오버와 다이얼로그 열기 | 1.2~1.8% |
| 펼친 메인 화면 | 통화 화면 조작 막대와 고정 | 0% |

펼친 메인 화면에서 팝오버와 다이얼로그를 열 때 끊긴 프레임은 대부분 큰 화면에서 글래스 블러를 그리는 비용이다. 단색 표면에서는 열 때 2프레임만 끊겼다.
